# Протокол проверки ERP MariaDB и 1С

## 1. Цель

Получить подтвержденные данные, на основании которых можно оформить полноценное ТЗ для PHP-разработчика без предположений о связях, формулах и ответах 1С.

Проверка выполняется на действующих ERP MariaDB и 1С. Тестовые Python/PostgreSQL/XLSX-компоненты не являются объектом проверки и не изменяются.

## 2. Результаты проверки

По завершении должны быть подготовлены:

1. обезличенный набор контрольных поставок;
2. SQL-файлы фактических выборок ERP;
3. обезличенные примеры SOAP-запросов и ответов 1С;
4. таблица ожидаемых значений восьми бухгалтерских колонок;
5. подтвержденный маппинг документов ERP ↔ 1С;
6. перечень ограничений первой версии;
7. протокол согласования бухгалтером.

## 3. Требования к контрольной выборке

В выборку включаются не менее 12 поставок. Одна поставка может закрывать несколько сценариев.

| ID | Сценарий | Обязательный результат |
|---|---|---|
| C01 | Прямой счет покупателю: `veda_schets.f_type = 1`, связь через `f_operid` | Счет найден один раз, сумма совпадает с карточкой ERP |
| C02 | Агрегирующий счет покупателю с дочерними строками `f_maininv` | В матрице отображается основной счет; его сумма не дублируется по операциям |
| C03 | Счет покупателю, связанный через `veda_schets_details_opers` | Счет и соответствующая операция найдены |
| C04 | Счет от поставщика: `veda_schets.f_type = 2` | Не попадает в клиентские колонки `Счет` и `Сумма по счету` |
| C05 | Оплата, связанная непосредственно со счетом (`f_doctype = 1`) | Используется распределенная сумма `f_clssum` |
| C06 | Оплата, связанная с операцией (`f_doctype = 3`) | Используется распределенная сумма `f_clssum` |
| C07 | Один банковский документ связан и со счетом, и с операцией | Одна и та же часть оплаты не учитывается дважды |
| C08 | Один банковский документ распределен между несколькими поставками | В каждой поставке видна только ее доля; сумма долей проверена |
| C09 | Операции поставки связаны напрямую (`f_parenttype = 2`) | Все операции попали в выборку |
| C10 | Операции поставки связаны через категорию (`f_parenttype = 4`, `veda_categs`) | Все операции попали в выборку |
| C11 | Возмещаемые операции `f_isvozm = 1` | Попадают только в возмещаемые расходы |
| C12 | Невозмещаемые операции `f_isvozm = 2` | Прямые клиентские акты попадают в невозмещаемые расходы; подрядные распределенные строки не включаются в клиентскую колонку и логируются отдельно |
| C13 | Операция с пустым/неизвестным `f_isvozm` | Не включается автоматически; выводится ошибка данных |
| C14 | Акт/УПД связан напрямую через `veda_akts.f_operid` | Документ найден один раз |
| C15 | Акт/УПД связан через `veda_akts_details_opers` | Использована доля строки текущей операции/поставки |
| C16 | Дочерний акт входит в основной через `f_mainakt` | Основной документ и сумма не дублируются |
| C17 | Несколько счетов-фактур/УПД на одну спецификацию | Все номера выведены полностью |
| C18 | Клиент имеет несколько ЮЛ, договоров и поставок | Иерархия и агрегаты построены по всем уровням |
| C19 | Документ выгружен, но не проведен в 1С | Статус выгрузки отделен от результата сверки |
| C20 | Документ проведен в 1С | Статус подтвержден ответом 1С |
| C21 | Документ ERP отсутствует в 1С | `Нет в 1С`, только если источник 1С успешно ответил |
| C22 | Документ 1С отсутствует в ERP в выбранном контексте | `Нет в ERP` |
| C23 | Сумма ERP и 1С расходится | `Расходится сумма`, указана разница |
| C24 | Расходится договор, организация, номер или дата | Указана конкретная причина, не общий статус НДС |
| C25 | 1С недоступна или вернула ошибку | `Ошибка источника 1С`; документы не помечаются `Нет в 1С` |
| C26 | Смешанные валюты в одной поставке/договоре | Суммы не складываются без утвержденного пересчета |
| C27 | XLSX с несколькими счетами одной спецификации | Объединенные ячейки соответствуют бухгалтерскому шаблону |
| C28 | Копирование того же блока | Получен плоский TSV с повторением значений объединенных ячеек |

## 4. Порядок проверки одной поставки

Для каждого контрольного `spec_id` выполняются следующие шаги.

### Шаг 1. Контекст

Зафиксировать:

- `spec_id` и номер спецификации;
- клиента и ЮЛ;
- договор;
- организацию ERP;
- период документов;
- коды 1С клиента, организации, договора и спецификации.

### Шаг 2. Операции ERP

Получить все операции двумя путями:

```sql
SELECT si.*
FROM veda_spec_invoices si
LEFT JOIN veda_categs c
       ON c.f_objectid = si.f_id
      AND c.f_ctgtype = 24
      AND c.f_objecttype = 5
WHERE
      (si.f_parenttype = 2 AND si.f_specid = :spec_id)
   OR (si.f_parenttype = 4 AND CAST(c.f_valstr AS SIGNED) = :spec_id);
```

Контроль:

- операции не потеряны;
- одна операция не продублирована;
- для каждой операции зафиксированы `f_isvozm`, тип операции, валюта, НДС и действующие расчетные функции ERP.

### Шаг 3. Счета покупателю

Проверить все типы связи:

1. `veda_schets.f_operid = oper_id`;
2. дочерний счет операции с `f_maininv`;
3. связь через `veda_schets_details_opers`;
4. счет, привязанный непосредственно к спецификации, если такой сценарий применяется в ERP.

Фильтр клиентских счетов:

```sql
veda_schets.f_type = 1
```

Контроль:

- `f_type = 2` не попадает в клиентскую колонку;
- агрегирующий основной счет учитывается один раз;
- сумма и валюта совпадают с карточкой счета ERP;
- определен надежный ключ документа 1С.

### Шаг 4. Оплаты

Получить распределения из `veda_acchist_docs`:

- `f_doctype = 1` — связь со счетом;
- `f_doctype = 3` — связь с операцией.

В расчет включается `f_clssum`.

Для каждого платежа сформировать контрольную таблицу:

| payment_id | Полная сумма | Тип связи | doc_id | spec_id | Распределенная сумма | Включено в итог |
|---|---:|---|---:|---:|---:|---:|

Сумма включенных долей не должна превышать распределения банковского документа. Алгоритм устранения двойного учета должен быть зафиксирован как отдельное правило финального ТЗ.

### Шаг 5. Расходы

Операции разделяются исключительно по `veda_spec_invoices.f_isvozm`.

Для каждой операции зафиксировать:

| oper_id | f_isvozm | Категория | Сумма операции | get_expensessum | get_realizsum | get_profit | Сумма для матрицы | Обоснование |
|---:|---:|---|---:|---:|---:|---:|---:|---|

Для клиентской матрицы отдельно проверить источник суммы:

- прямой акт `veda_akts.f_operid` по операции с `f_isvozm = 2` включается в `Невозмещаемые расходы`;
- распределенная подрядная строка `veda_akts_details_opers.f_sum` по операции с `f_isvozm = 2` не включается в клиентскую колонку и попадает в журнал как исключенный подрядный расход;
- операции с `f_isvozm = 1` могут попадать в `Возмещаемые расходы` и через прямой акт, и через распределенную строку акта.

Аналитик и бухгалтер должны подтвердить, какое фактическое значение используется для каждой колонки в действующей ERP. После этого правило переносится в финальное ТЗ без изменения бизнес-логики.

### Шаг 6. Акты, УПД и счет-фактуры

Проверить:

- прямую связь `veda_akts.f_operid`;
- связь через `veda_akts_details_opers`;
- агрегирование через `f_mainakt`;
- распределенную сумму строки;
- источник фактического номера счет-фактуры/УПД;
- статус документа и ключ 1С.

Технический код 1С, номер акта и номер счет-фактуры фиксируются разными полями.

### Шаг 7. Ответы 1С

Вызвать действующие PHP/SOAP-методы для того же контекста. Для каждого типа документа сохранить обезличенный пример ответа и заполнить таблицу:

| Тип документа | SOAP-метод | Поле ключа | Номер | Дата | Организация | Контрагент | Договор | Сумма | Валюта | Статус проведения |
|---|---|---|---|---|---|---|---|---:|---|---|

Если существующий метод не возвращает обязательное поле, это оформляется как требование на доработку 1С-сервиса, а не компенсируется ненадежной текстовой эвристикой в UI.

### Шаг 8. Сопоставление

Проверить приоритеты:

1. технический ключ 1С + тип документа;
2. номер + дата + организация + контрагент + договор;
3. сумма — только контроль найденного кандидата;
4. несколько кандидатов — отдельный статус;
5. ошибка источника — отдельный статус.

### Шаг 9. Итоги и XLSX

Для каждой спецификации заполнить ожидаемый блок:

| № спецификации | Счет | Сумма по счету | Сумма оплаты | Возмещаемые расходы | Невозмещаемые расходы | № счф | (+/-) |
|---|---|---:|---:|---:|---:|---|---:|

Проверить:

- формулу `(+/-)`;
- отсутствие двойного учета;
- совпадение экранных итогов, копирования и XLSX;
- корректность объединенных ячеек;
- числовой тип денежных ячеек.

## 5. Обязательные артефакты по каждому кейсу

Для каждого `Cxx` сохраняются:

- идентификатор обезличенного кейса;
- `spec_id` во внутреннем закрытом протоколе;
- SQL и результат ERP;
- SOAP-метод, параметры и обезличенный ответ;
- рассчитанные восемь колонок;
- фактический скрин/выгрузка ERP;
- решение аналитика;
- подтверждение бухгалтера;
- статус `Пройден / Не пройден / Ограничение`.

## 6. Критерии готовности к финальному ТЗ

Финальное ТЗ готовится, когда:

- все C01–C28 выполнены либо для неприменимых сценариев есть обоснование;
- C01–C25 не имеют нерешенных расхождений уровня блокировки;
- формулы восьми колонок подтверждены бухгалтером;
- входные и выходные поля SOAP зафиксированы;
- определены изменения PHP ERP и, при необходимости, 1С-сервиса;
- тестовые примеры воспроизводятся повторным запуском;
- известны ограничения по валютам, корректировкам и агрегирующим документам.
