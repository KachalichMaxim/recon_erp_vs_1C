# Автоматические тесты логики матрицы сверки

## Назначение

Тесты фиксируют эталонную логику интерфейса матрицы до подключения к действующим ERP MariaDB и 1С. Они не заменяют протокол ручной проверки `C01-C28`, а защищают от регрессий в правилах, которые можно проверить без живых источников.

Референсная логика вынесена в `ui/reconciliation_matrix_logic.mjs`. Интерфейс и проверки должны развиваться от этих же правил:

- возмещаемость определяется только числом `f_isvozm`;
- тип счета определяется только числом `f_type`;
- оплаты считаются по распределенной сумме `f_clssum`;
- счет покупателю и счет поставщика не смешиваются;
- НДС является отдельным расхождением ставки НДС, а не синонимом любого несуммового расхождения;
- `Нет СФ/УПД` является отдельным кодом сверки или подтвержденным отсутствием закрывающего документа, а не следствием возмещаемости;
- копирование формирует плоский TSV, где значения объединенных ячеек повторяются;
- XLSX-раскладка сохраняет объединенные колонки бухгалтерского шаблона.

## Запуск

```bash
npm test
```

Команда запускает встроенный Node.js test runner и не требует подключения к MariaDB, SOAP, внешним аналитическим хранилищам или Python-сервису. Проверки используют уже сохраненные JSON-артефакты.

После текущей проверки сохранен визуальный артефакт интерфейса: `screenshots/ui/matrix_after_reference_tests.png`.

## Покрытие сценариев

| Сценарий | Проверка в автотестах |
|---|---|
| C01 | Прямой счет покупателю включается в колонку `Счет` |
| C02 | Агрегирующий счет через `f_maininv` учитывается один раз |
| C03 | Счет через детализацию операции попадает в матрицу |
| C04 | `f_type = 2` не попадает в клиентскую колонку счета |
| C05 | Оплата по счету учитывается по `f_clssum` |
| C06 | Оплата по операции учитывается по `f_clssum` |
| C07 | Одна оплата, связанная и со счетом, и с операцией, не удваивается |
| C08 | Распределение платежа вне текущей поставки не попадает в итог |
| C09 | Операция с `f_parenttype = 2` включается |
| C10 | Операция с `f_parenttype = 4` через категорию включается |
| C11 | `f_isvozm = 1` попадает только в возмещаемые расходы |
| C12 | Прямые клиентские акты с `f_isvozm = 2` попадают в невозмещаемые расходы; подрядные распределенные строки `veda_akts_details_opers` с `f_isvozm = 2` исключаются из клиентской колонки |
| C13 | Пустой/неизвестный `f_isvozm` не попадает в расходы и дает ошибку данных |
| C14 | Акт/УПД по прямой связи операции найден |
| C15 | Акт/УПД через детализацию операции найден |
| C16 | Дочерний акт через `f_mainakt` не дублирует основной |
| C17 | Все номера СФ/УПД выводятся полностью, без `+N` |
| C18 | Иерархия строится как клиент → ЮЛ → договор → спецификация |
| C23 | Расхождение суммы дает отдельный статус суммы |
| C24 | Расхождение даты/договора/организации не превращается в НДС |
| C25 | Ошибка источника 1С не превращается в `Нет в 1С` |
| C26 | Смешанные валюты не складываются в один итог без правила пересчета |
| C27 | Для XLSX зафиксированы объединяемые бухгалтерские колонки |
| C28 | Копирование TSV повторяет значения объединенных ячеек в плоских строках |

Сценарии C19-C22 требуют фактических SOAP-ответов 1С и остаются в ручном validation-протоколе до появления обезличенных ответов.

## Важные ожидания для PHP-разработки

### Возмещаемость

Разработчик не должен определять возмещаемость по названию операции, комментарию, НДС или тексту справочника. Допустимы только значения:

```text
f_isvozm = 1 -> возмещаемые расходы
f_isvozm = 2 -> невозмещаемые расходы
```

Любое другое значение попадает в журнал ошибок качества данных и не увеличивает суммы колонок расходов.

### Счета

В клиентскую колонку `Счет` попадают только счета покупателю:

```text
veda_schets.f_type = 1
```

Счета поставщиков (`f_type = 2`) могут участвовать в технической детализации расходов, но не выводятся как клиентские счета.

### Оплаты

В итог попадает не полная сумма банковского документа, а распределенная сумма:

```text
veda_acchist_docs.f_clssum
```

Если одна часть оплаты связана и со счетом, и с операцией, приоритет имеет связь со счетом. Это правило в тестах нужно подтвердить на живой ERP перед переносом в финальное ТЗ.

### СФ/УПД и НДС

`Нет СФ/УПД` и `Вопрос по НДС` являются разными статусами.

- `Нет СФ/УПД` — нет связанного закрывающего документа при успешном источнике 1С.
- `Вопрос по НДС` — ставка НДС ERP и ставка НДС 1С различаются.
- Расхождение даты, номера, договора или организации получает статус `Расходятся реквизиты`.

### Копирование и XLSX

На экране и в XLSX номера документов показываются полностью, каждый с новой строки. В TSV для копирования переносы строк внутри ячеек заменяются на ` / `, чтобы вставка в таблицу клиента не ломала количество строк.
