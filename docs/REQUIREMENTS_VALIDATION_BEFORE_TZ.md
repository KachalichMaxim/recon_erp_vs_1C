# Требования к проверке логики ERP ↔ 1С перед подготовкой финального ТЗ

## 1. Назначение документа

Документ фиксирует, **что необходимо проверить на действующих ERP MariaDB и 1С**, какие правила уже считаются подтвержденными и какие результаты должны быть получены до оформления финального ТЗ на новую PHP-страницу ERP.

Это не финальное ТЗ разработчику. После прохождения проверок из этого документа аналитик должен заменить допущения подтвержденными SQL-связями, полями SOAP-ответов, формулами и контрольными примерами.

## 2. Границы промышленного решения

Целевой контур первой версии:

1. PHP-страница внутри существующей ERP.
2. Источник ERP — действующая MariaDB.
3. Источник 1С — действующая 1С через существующий PHP/SOAP-слой.
4. Сравнение и формирование XLSX выполняются на стороне ERP.
5. Внешние аналитические файлы не являются обязательными компонентами промышленной реализации и не должны использоваться как источник данных промышленной сверки.

В рамках этой проверки достаточно подтвердить SQL-связи на действующей MariaDB ERP и SOAP-ответы 1С; внешние аналитические файлы могут использоваться только как подсказка по формату, но не как источник сумм.

## 3. Подтвержденные бизнес-правила

### 3.1. Возмещаемость

Классификация операции определяется полем `veda_spec_invoices.f_isvozm`, но включение суммы в клиентскую матрицу зависит от источника суммы:

- `f_isvozm = 1` — возмещаемые расходы;
- `f_isvozm = 2` — невозмещаемые расходы;
- другое или незаполненное значение — операция не должна автоматически попадать ни в одну категорию; это отдельная ошибка качества данных.

Запрещено определять возмещаемость по названию операции, комментарию, НДС, типу документа или тексту строки 1С.

Для клиентской матрицы подтверждено уточнение: прямые клиентские акты `veda_akts.f_operid` с `f_isvozm = 2` попадают в колонку `Невозмещаемые расходы`, а подрядные распределенные строки `veda_akts_details_opers` с `f_isvozm = 2` не включаются в клиентский взаиморасчет и должны логироваться отдельно. Это покрывает кейс, где агент пользуется услугами подрядчика и не должен подтягивать договор клиента к подрядному расходу.

Поле `f_isvozm` определяет категорию операции. **Сумма** внутри категории должна рассчитываться тем же действующим алгоритмом ERP, который используется в текущих отчетах и формах, с учетом типа источника суммы: прямой акт или распределенная строка акта.

### 3.2. Тип счета

Для `veda_schets.f_type` используется следующее правило:

- `f_type = 1` — счет покупателю;
- `f_type = 2` — счет от поставщика.

В колонках `Счет` и `Сумма по счету` клиентской сверки участвуют только счета покупателю (`f_type = 1`). Счета поставщиков могут использоваться в детализации расходов, но не должны попадать в клиентскую колонку счета.

### 3.3. Формат бухгалтерской XLSX

Вертикально объединенные ячейки в блоке одной спецификации являются требованием бухгалтерии и должны быть сохранены.

Обязательные бизнес-колонки:

1. `№ спецификации`;
2. `Счет`;
3. `Сумма по счету`;
4. `Сумма оплаты`;
5. `Возмещаемые расходы`;
6. `Невозмещаемые расходы`;
7. `№ счф`;
8. `(+/-)`.

Визуальные пустые колонки-разделители допустимы только в XLSX-шаблоне. Они не являются бизнес-данными.

Для действия `Скопировать` система должна формировать плоский табличный набор: значения из объединенных ячеек повторяются в каждой копируемой строке. Это позволяет вставить данные в таблицу клиента без потери контекста.

## 4. Целевой пользовательский поток

1. Бухгалтер открывает страницу сверки из ERP или из карточки поставки.
2. Выбирает клиента и период.
3. Видит иерархию:
   `Клиент → ЮЛ клиента → договор → поставка/спецификация`.
4. Раскрывает поставку и видит связанные счета, оплаты, закрывающие документы и результаты сверки с 1С.
5. Для каждого документа отдельно видит:
   - статус выгрузки/проведения в 1С;
   - результат сравнения ERP ↔ 1С.
6. Фильтрует только проблемные строки.
7. Копирует данные для таблицы клиента либо формирует XLSX в привычном бухгалтерском формате.

## 5. Обязательные связи ERP

| Уровень/объект | Основная связь | Что необходимо проверить |
|---|---|---|
| Клиент → ЮЛ | `veda_contacts.f_id = veda_clients.f_contactid` | Все ЮЛ выбранного клиента доступны в дереве |
| ЮЛ → договоры | `veda_clients.f_id = veda_dogs.f_contrid` | Договоры не смешиваются между ЮЛ |
| Договор → поставки | `veda_dogs.f_id = veda_specs.f_dogid` | Возвращаются все поставки периода, а не только текущий `spec_id` |
| Поставка → операции | `f_parenttype = 2 AND f_specid = spec_id` | Прямая связь |
| Поставка → операции | `f_parenttype = 4` через `veda_categs`, `f_ctgtype = 24`, `f_objecttype = 5` | Альтернативная связь не должна теряться |
| Операция → счет | `veda_schets.f_operid` | Прямой счет покупателю |
| Операция → агрегирующий счет | дочерний счет через `f_maininv` | Сумма основного счета не дублируется по дочерним строкам |
| Операция → строка счета | `veda_schets_details_opers` | Учитываются счета, связанные через детализацию |
| Счет/операция → оплата | `veda_acchist_docs` | Используется распределенная сумма `f_clssum` |
| Операция → акт | `veda_akts.f_operid` | Прямая связь |
| Операция → строка акта | `veda_akts_details_opers` | Используется доля строки, относящаяся к операции |
| Дочерний акт → основной акт | `veda_akts.f_mainakt` | Основной документ не дублируется |

До финального ТЗ каждая связь должна быть подтверждена минимум одним реальным примером из действующей ERP.

## 6. Правила колонок матрицы

### 6.1. № спецификации

Источник — `veda_specs.f_num`. В интерфейсе строка относится к конкретному `spec_id`, даже если номера спецификаций повторяются в разных договорах.

### 6.2. Счет и сумма по счету

- Учитываются только счета покупателю: `veda_schets.f_type = 1`.
- Основной счет отображается один раз.
- Для агрегирующего счета дочерние строки используются для связи с операциями, но не должны повторно увеличивать сумму основного счета.
- Счет поставщика (`f_type = 2`) не выводится в клиентской колонке `Счет`.
- Валюта счета должна передаваться отдельно; суммы разных валют не складываются без утвержденного правила пересчета.

### 6.3. Сумма оплаты

- Используется распределенная сумма `veda_acchist_docs.f_clssum`, а не полная сумма банковского документа.
- Необходимо учитывать обе действующие связи: со счетом (`f_doctype = 1`) и с операцией (`f_doctype = 3`).
- Должен быть утвержден алгоритм приоритета, исключающий двойной учет одной и той же части оплаты.
- В деталях пользователь должен иметь возможность открыть платеж и увидеть полную сумму платежа и долю, отнесенную на текущую поставку.

### 6.4. Возмещаемые и невозмещаемые расходы

1. Операции сначала разделяются по `veda_spec_invoices.f_isvozm`.
2. Возмещаемые расходы клиентской матрицы считаются как сумма прямых актов `veda_akts.f_operid` и распределений `veda_akts_details_opers.f_sum` по операциям с `f_isvozm = 1`.
3. Невозмещаемые расходы клиентской матрицы считаются по прямым клиентским актам `veda_akts.f_operid` с `f_isvozm = 2`.
4. Распределенные подрядные строки `veda_akts_details_opers` с `f_isvozm = 2` не увеличивают колонку клиента; они попадают в журнал как исключенные подрядные расходы.
5. Операция с неопределенным `f_isvozm` не включается автоматически и получает отдельный статус ошибки данных.
6. Текущую функцию/SQL расчета суммы необходимо подтвердить на реальной ERP и указать в финальном ТЗ.

### 6.5. № счф

До финального ТЗ требуется подтвердить фактический источник номера счета-фактуры/УПД в ERP и связь с поставкой. В колонке должен отображаться бухгалтерский номер документа, а не технический ID, код 1С или номер другого типа документа.

Если с поставкой связано несколько документов, номера выводятся полностью, каждый с новой строки в объединенной ячейке XLSX.

### 6.6. (+/-)

Базовая формула блока спецификации:

`Сумма оплаты − Возмещаемые расходы − Невозмещаемые расходы`.

Допуск сравнения — `0,01`. Для нескольких валют общий показатель не рассчитывается до утверждения единого правила пересчета; интерфейс должен показать причину `Смешанные валюты`.

## 7. Сверка с 1С

### 7.1. Источник

Проверка выполняется через существующий PHP/SOAP-слой ERP. Перед разработкой необходимо снять и сохранить обезличенные примеры фактических ответов 1С минимум для:

- счетов покупателю;
- поступлений оплаты;
- актов/УПД/реализаций;
- договоров/договоров-заявок;
- актов сверки, если они используются как контроль итогов.

Для каждого метода фиксируются входные параметры, поля ответа, типы данных, правила пустых значений и ошибки SOAP.

### 7.2. Приоритет сопоставления

1. Надежный технический ключ 1С + тип документа.
2. Если надежного ключа нет — номер + дата + организация + контрагент + договор.
3. Сумма используется для проверки найденного кандидата, а не как единственный ключ.
4. При нескольких кандидатах автоматический `ОК` запрещен; статус — `Неоднозначное соответствие`.
5. Недоступность 1С является ошибкой источника и не должна превращаться в статус `Нет в 1С` для всех документов.

## 8. Статусы

### 8.1. Статус выгрузки в 1С

Отображается отдельно для каждого документа:

- `Не выгружен`;
- `Выгружен, не проведен`;
- `Проведен в 1С`;
- `Помечен на удаление`;
- `Ключ 1С есть, статус не определен`.

Коды ERP, соответствующие этим состояниям, необходимо подтвердить по действующему справочнику статусов.

### 8.2. Результат сверки ERP ↔ 1С

- `Совпадает`;
- `Нет в 1С`;
- `Нет в ERP`;
- `Расходится сумма`;
- `Расходится номер/дата`;
- `Расходится договор/организация`;
- `Нет ключа 1С`;
- `Неоднозначное соответствие`;
- `Недостаточно данных`;
- `Ошибка источника 1С`.

Причина должна передаваться с backend как код и набор конкретных полей. UI не должен определять тип ошибки по тексту названия документа или операции.

## 9. Требования к интерфейсу

### 9.1. Матрица

- Первая колонка и заголовок закреплены.
- Денежные значения выровнены вправо.
- Родительские строки показывают агрегаты дочерних поставок.
- Документы раскрываются внутри поставки.
- В строке документа доступны два независимых статуса: выгрузка и сверка.
- Поиск работает по клиенту, ЮЛ, договору, спецификации, счету и номеру документа.
- Для больших клиентов договоры и поставки загружаются лениво.

### 9.2. Режим ошибок

Режим является фильтром той же матрицы. Для выбранной ошибки показываются:

- поле;
- значение ERP;
- значение 1С;
- разница;
- правило сравнения;
- источник данных;
- рекомендуемое действие.

Нельзя обозначать любое несуммовое расхождение как ошибку НДС.

### 9.3. Копирование

Кнопка `Скопировать` формирует TSV по выбранному клиенту/договору/поставке. Значения объединенных ячеек повторяются в каждой строке. Результат не зависит от того, какие ветки дерева сейчас раскрыты.

## 10. Требования к XLSX

1. Первый лист — бухгалтерская ведомость с привычными объединенными блоками.
2. Одна спецификация — один вертикальный блок строк счетов.
3. `№ спецификации`, итоговые расходы, `№ счф` и `(+/-)` объединяются по высоте блока, если это соответствует утвержденному шаблону бухгалтерии.
4. Счета и относящиеся к ним оплаты выводятся построчно.
5. Денежные значения сохраняются числами, а не строками с символом валюты.
6. Второй технический лист допустим для детализации ERP ↔ 1С, но не обязателен для передачи клиенту.
7. Экран, копирование и XLSX должны формироваться из одного серверного набора данных и давать одинаковые итоги.

## 11. Что требуется до оформления финального ТЗ

Финальное ТЗ можно оформлять после выполнения всех условий:

- подтверждены SQL-связи на действующей MariaDB;
- подтверждены фактические SOAP-ответы 1С;
- утвержден алгоритм суммы по каждой из восьми колонок;
- подтвержден алгоритм исключения двойного учета оплат;
- подтвержден источник `№ счф`;
- утверждены коды статусов выгрузки;
- пройдена матрица контрольных кейсов;
- бухгалтер подтвердил итоговые значения и внешний вид XLSX;
- зафиксирован список ограничений первой версии.

## 12. Вне первой версии

Если отдельно не согласовано, в первую версию не включаются:

- изменение документов или справочников 1С;
- автоматическая ручная привязка документов без журнала решений;
- изменение тестового Python/PostgreSQL-контура;
- обязательная загрузка аналитических XLSX как источник промышленной сверки;
- замена существующего PHP/SOAP-обмена новым сервисом.
